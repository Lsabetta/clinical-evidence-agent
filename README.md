# Clinical Evidence Agent
**Status:** under active development. The current implementation provides two non-agentic baselines (V0A and V0B). Agent-controlled retrieval is planned; the system is not clinically validated.

A research project studying whether agent-controlled retrieval improves biomedical evidence answers over simpler LLM workflows.

The system accepts a natural-language biomedical research question and returns a structured answer. Development starts with measurable baselines, then adds tool use and adaptive retrieval incrementally.

**Research support only.** This is an experimental system, not a clinically validated product or a source of individualized diagnosis or treatment advice. It uses public biomedical literature, not private patient data.

## Implemented baselines

The published code currently provides two **non-agentic** pipelines:

| Pipeline | Evidence access | Control flow |
| --- | --- | --- |
| **V0A** | No external retrieval | One LLM call; application code sets `evidence_status = "not_assessed"` and `sources = []`. |
| **V0B** | PubMed metadata and available abstracts | One LLM-generated query, one search, batch retrieval of up to top-k records, one synthesis call, and citation-consistency checks. |

V0B uses fixed application control flow. The model does not decide which tools to invoke, revise its query, or repeat retrieval. Fixed control flow does not imply identical model outputs or live PubMed results.

The research question is whether later adaptive retrieval improves relevance and answer grounding enough to justify its latency, token usage, and implementation complexity. No advantage from agency has been demonstrated.

## Quick start

Requirements: Python 3.12+, [uv](https://docs.astral.sh/uv/), and a running [Ollama](https://ollama.com/) server. V0B also requires network access to NCBI E-utilities.

```bash
git clone https://github.com/Lsabetta/clinical-evidence-agent.git
cd clinical-evidence-agent
uv sync --locked
ollama pull qwen3:4b-instruct
```

Start Ollama with `ollama serve` in a separate terminal if it is not already running.

Run the LLM-only baseline:

```bash
uv run clinical-evidence-agent \
  "What evidence supports exercise for fatigue in adults with multiple sclerosis?" \
  --pipeline v0a
```

Run the PubMed baseline:

```bash
uv run clinical-evidence-agent \
  "What evidence supports exercise for fatigue in adults with multiple sclerosis?" \
  --pipeline v0b --top-k 3
```

The default pipeline is `v0a`; the default V0B retrieval limit is three records. Questions must be non-empty and `--top-k` must be positive.

The model is configured in [llm.py](src/clinical_evidence_agent/llm.py), currently as `qwen3:4b-instruct` with temperature 0. There is no CLI model selector. The published adapter does not explicitly set the context window; long evidence inputs can exceed the available context.

## Output and run records

Both pipelines return the same Pydantic-validated `EvidenceAnswer`:

| Field | Meaning |
| --- | --- |
| `question_status` | `well_specified`, `underspecified`, or `out_of_scope`. |
| `evidence_status` | `sufficient`, `partial`, `insufficient`, or `not_assessed`. V0A always uses `not_assessed`. |
| `summary` | A concise answer; V0B is instructed to cite supplied evidence inline as `[PMID: 123]`. |
| `sources` | Cited records, with PMID, optional PMCID, title, and URL. Empty for V0A. |
| `limitations` | Evidence gaps and restrictions on interpretation. |

Evidence status is a model assessment, not an independently verified confidence score. Source metadata is assembled from retrieved records rather than generated by the model.

The CLI prints the answer as JSON and writes JSONL logs relative to the working directory:

- `runs/v0a.jsonl`: input, model, prompt version, answer, latency, token usage, and errors.
- `runs/v0b.jsonl`: generated query, ordered evidence snapshot, synthesis draft, final answer, stage timings, token usage, and partial results on failure.

PubMed warnings can currently also be printed to standard output, so CLI stdout is not guaranteed to contain only JSON.

## Tests and evaluation

Run automated tests:

```bash
uv run pytest
```

Validate the smoke dataset without calling the model or PubMed:

```bash
uv run python eval/run_smoke.py
```

Execute both baselines on the ten-question smoke dataset:

```bash
uv run python eval/run_smoke.py --run
```

Results are saved under `eval/results/<timestamp>/`, including the dataset, protocol, per-case outputs, errors, run logs, and an execution index. Real-model runs can take several minutes per question depending on hardware and input length.

The [smoke protocol](eval/smoke_protocol.md) separates query fidelity, retrieval relevance, grounding, citation support, and question classification. Latency and token usage are recorded alongside these judgments. Automated validation alone does not measure clinical accuracy.

## Known limitations

- A generated query may distort the question or mishandle exclusions, and a single top-k search can miss relevant studies.
- Only metadata and available abstracts are retrieved. Full text is not supplied.
- Citation checks establish consistency between recognized inline PMIDs, declared citations, and retrieved records. They do not establish that a cited paper supports a claim or that every claim is cited. The published validator can miss malformed citation markers.
- Unsupported or contradicted synthesis claims have been observed even when schema and citation checks pass.
- Empty retrieval does not establish that relevant evidence does not exist.
- Live PubMed results can vary between otherwise identical requests. Saved evidence snapshots support inspection and synthesis replay.
- Structured-output failures do not currently preserve the raw invalid model response.

The separate exploratory review dated 2026-10-05 reported successful execution for 10/10 V0A cases and 8/10 V0B cases, with substantive answer-quality failures. Execution success is not evidence of clinical correctness or superiority of either pipeline. The report and subsequent fixes are not included in this published snapshot; `current_state.md` still describes the comparison as pending.

## Roadmap

The [project strategy](project_documentation/project_strategy.md) develops complexity in stages:

1. **V0:** preserve LLM-only and fixed PubMed baselines.
2. **V1:** implement a manual tool-calling loop and evaluate adaptive retrieval.
3. **V2:** explore iterative retrieval and explicit workflow state with LangGraph.
4. **V3:** add verification and broader evaluation.
5. **V4, optional:** investigate additional sources or architectures only when justified by experiments.

V1 and later stages are not implemented in the current published code. Frameworks, verifiers, and multi-agent systems are future work, not current capabilities.
